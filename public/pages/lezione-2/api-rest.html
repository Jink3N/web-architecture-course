🌐 API REST

REST (Representational State Transfer) è uno stile architetturale per costruire API semplici, scalabili e facili da capire. Qui impariamo le basi per progettare endpoint chiari e sicuri.

🔎 Che cos'è un'API?

API significa Application Programming Interface: un contratto che descrive come due applicazioni possono parlarsi. Nel web, un'API espone URL che accettano richieste HTTP e rispondono con dati, spesso in formato JSON.

Principi base REST

  • Client-Server: separa chi richiede il dato (client) da chi lo fornisce (server).
  • Stateless: ogni richiesta contiene tutte le informazioni necessarie. Il server non ricorda lo stato tra due richieste.
  • Uniform Interface: regole coerenti per tutti gli endpoint (stessi verbi HTTP, strutture prevedibili).
  • Cacheable: le risposte possono essere memorizzate per migliorare le performance.

🧭 Progettare gli endpoint

Risorse e URL

Ogni endpoint rappresenta una risorsa (es. utenti, ordini). Gli URL dovrebbero usare sostantivi al plurale e gerarchie chiare. 

GET /api/users          → elenco utenti
GET /api/users/42      → utente con id 42
POST /api/users        → crea un nuovo utente
GET /api/users/42/orders → ordini dell'utente 42

✅ Fai così

  • Usa verbi HTTP coerenti
  • Struttura prevedibile
  • Versiona l'API (/api/v1/)

❌ Evita

  • Mescolare verbi negli URL (/getUsers)
  • Restituire HTML inatteso
  • Endpoint con significati ambigui

🧾 Metodi HTTP e codici di stato

Metodo Uso tipico Codici di risposta comuni
GET Leggere dati senza modificarli 200 OK, 404 Not Found
POST Creare una nuova risorsa 201 Created, 400 Bad Request
PUT Sostituire completamente una risorsa 200 OK, 204 No Content
PATCH Aggiornare parzialmente una risorsa 200 OK, 204 No Content
DELETE Eliminare una risorsa 204 No Content, 404 Not Found

Codici di stato spiegati

I codici HTTP indicano l'esito della richiesta. 2xx = successo, 4xx = errore del client, 5xx = errore del server.

📦 Struttura di richiesta e risposta

// Richiesta (client → server)
POST /api/v1/users
Content-Type: application/json

{
  "name": "Ada Lovelace",
  "email": "ada@example.com"
}

// Risposta (server → client)
HTTP/1.1 201 Created
Location: /api/v1/users/101
Content-Type: application/json

{
  "id": 101,
  "name": "Ada Lovelace",
  "email": "ada@example.com"
}

🏗️ Best practices

  • Documenta gli endpoint con esempi (OpenAPI/Swagger).
  • Valida sempre i dati in ingresso (es. librerie Joi, zod).
  • Usa versionamento per gestire evoluzioni senza rompere i client.
  • Restituisci errori chiari con messaggi utili e codici coerenti.

🚧 Errori da evitare

  • Mescolare logica di business e logica di trasporto (HTTP) nello stesso livello di codice.
  • Non controllare gli input: apertura a SQL injection o crash.
  • Esportare dati sensibili in risposta (password hash, token).
  • Utilizzare codici HTTP generici come 200 anche in caso di errore.

🛡️ Sicurezza senza autenticazione

  • HTTPS obbligatorio: protegge i dati in transito.
  • Rate limiting: limita il numero di richieste per IP per prevenire abusi.
  • CORS controllato: permette solo domini conosciuti.
  • Logging & Monitoring: registra richieste sospette e attiva alert.

📚 Glossario essenziale

Payload
Il corpo della richiesta o della risposta. Spesso JSON.
Idempotente
Operazione che produce lo stesso risultato se ripetuta (es. PUT, DELETE).
Resource
Oggetto logico dell'API (utente, ordine, prodotto).
Representation
Il formato con cui la risorsa viene restituita (JSON, XML).

🏥 Caso reale: API per prenotazioni sanitarie

Un'azienda ospedaliera mette a disposizione un'API per gestire le prenotazioni delle visite. I client (app mobile, sportelli) usano la stessa interfaccia per cercare disponibilità, prenotare o disdire appuntamenti.

Struttura degli endpoint

GET    /api/v1/clinics                   → elenco ambulatori
GET    /api/v1/clinics/:id/slots         → slot liberi per l'ambulatorio
POST   /api/v1/bookings                  → crea prenotazione
PATCH  /api/v1/bookings/:id/status       → conferma o annulla
DELETE /api/v1/bookings/:id              → elimina prenotazione

Esempio di risposta reale

GET /api/v1/clinics/45/slots?date=2025-10-10

{
  "clinicId": 45,
  "speciality": "Cardiologia",
  "slots": [
    { "start": "09:00", "end": "09:30", "availability": "free" },
    { "start": "09:30", "end": "10:00", "availability": "booked" },
    { "start": "10:00", "end": "10:30", "availability": "free" }
  ]
}

Lezioni dal caso reale

  • Versionamento: /api/v1 permette di pubblicare una seconda versione senza rompere i client esistenti.
  • Uso di PATCH per aggiornare solo lo stato (es. conferma visita) evita di reinviare tutti i dati.
  • La documentazione descrive vincoli: massimo 2 prenotazioni attive per utente, slot prenotabili entro 30 giorni.
